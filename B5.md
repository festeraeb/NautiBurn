# B5 — P100 GEMM, dtype lock

Closed on the cesarops2 P100. The measured max abs error is **2.74576247e-3**. The tolerance written in `crates/nautiburn-layer0/src/main.rs` before the run is **5e-2**. Expert ids match the oracle on all 128 tokens.

## Call site

`gemm_cubecl` in `crates/nautiburn-layer0/src/main.rs`. It is `Tensor::matmul`. On this CUDA backend that is CubeCL. Nothing else in the block multiplies matrices. The CPU miss path is `gemm_cpu` and does not call it.

CubeCL's CUDA C++ compiler is enabled (`cubecl-cuda` feature `cpp`), so the GEMM is JIT'd with nvrtc. The process mapped

- `/tmp/nautiburn-b0/cuda12-nvrtc/libnvrtc.so`
- `/tmp/nautiburn-b0/cuda12-nvrtc/libnvrtc-builtins.so.12.8`

That directory is the CUDA 12.8.93 nvrtc staged in B0. `libnvrtc.so.13` was not mapped.

## Block

OLMoE layer 0 from `olmoe-1b-7b-0924-f16.gguf`: gate, top-8, SwiGLU expert GEMM, weighted combine. 128 frozen hidden vectors, each scaled to RMS 1. Seed `20260924`. Not a prompt.

The oracle is the ivy llama.cpp ggml CUDA runtime (`b5/olmoe_layer0_oracle.cpp`), the same op sequence as `build_moe_ffn` in `olmoe.cpp`: `mul_mat`, softmax, `argsort_top_k`, `mul_mat_id`, `swiglu_split`, weight, add. `norm_w` is false. No Q4.

## Dtypes

FP16 was tried first. CubeCL refused the launch: the kernel requests 69632 bytes of shared memory and the P100 allows 49152 per cube. The gate GEMM and the expert GEMM were demoted to FP32 and the block was measured again. That second number is the one above.

Softmax and top-k ran in FP32. The ggml oracle's `mul_mat` result is FP32, and the router weight in the file is already FP32. SiLU and the weighted combine followed the FP32 GEMM. The CPU expert is FP32.

## CPU miss

Expert **33** was left off the device. It is token 0's first selected expert, and 17 of the 128 tokens selected it. Those 17 rows were computed with `gemm_cpu` from the host copy. The other selected experts stayed on the CubeCL GEMM. Top-8 sets still matched the oracle (`id_mismatches=0`).
